data-graph

Lineage, checks and profiling for semantic layers written in Apache Ossie

A semantic model becomes a graph you can ask questions of.

https://github.com/digital-duck/data-graph
data-graph reads an Apache Ossie semantic model and turns it into a lineage graph. With that graph you can trace metrics, check the model and profile the data behind it. It is a prototype, and this talk shows what works today.

    The problem: trusting the answer

    Let an analyst ask a database questions in plain language, and trust the answer.

    • data-graph is the third attempt at this goal: data-copilot, then anadata, then data-graph.
    • The earlier tools sent the LLM's SQL on after a parse: is_sql_valid only parses.
    • Parsing says nothing about whether the SQL uses real tables, runs, or answers the question.
    Getting an LLM to write SQL is the easy part. The hard part is knowing whether to trust what it wrote. The earlier tools only checked that the SQL parsed.

    Two earlier attempts

    data-copilot (2023)

    Streamlit app on vanna.ai, through the fork ssadata
    ✔ Knowledge base: DDL, docs, question/SQL pairs, business terms
    ✔ Measured: 24 Chinook questions across ten models
    Logic in Streamlit pages and a 1,474-line utils.py, no tests
    The SQL was trusted; allow_llm_to_see_data=True

    anadata (2026)

    Its own AnaData class on the dd-* stack
    Same idea, with retrieval through dd-embed / dd-vectordb
    About 2,900 lines, no tests
    data-copilot got two things right: the knowledge-base idea, and measuring results on the 24 Chinook questions. What held it back was an engine it did not own, logic buried in the UI, no tests, and SQL that was trusted. anadata rebuilt the engine on the dd stack but also had no tests.

    The idea: a semantic model as a lineage graph

    • Read a model in Apache Ossie, an open YAML/JSON format for datasets, fields, metrics and joins.
    • Stack it in layers:
    • top metrics computed from fields
    • middle datasets and fields that read the tables
    • bottom physical source tables and columns

    With the graph

    ✔ lineage (upstream)
    ✔ impact (downstream)
    ✔ checks for gaps
    ✔ read-only profiling
    ✔ drawing and export
    A semantic layer already says what the context for a question should be. data-graph turns it into a graph, so questions about the model become graph walks.

    Apache Ossie, two shapes

    0.1.1 (released)0.3.0.dev0 (draft)
    documentsemantic_model: listone model at the root
    expressiondialectssql (authoritative)
    field typenonedatatype
    bundled schemaosi-0.1.1.schema.jsonossie-0.3.0.dev0.schema.json
    • Both shapes are read, and each is checked against its own schema in src/datagraf/schemas/.
    Ossie, formerly Open Semantic Interchange, is incubating at Apache and has two shapes in use. The released 0.1.1 and the 0.3.0 draft are both supported. Expression text comes from sql, or else the OSSIE_SQL_2026 or ANSI_SQL dialect entry.

    The graph

    idfrom
    source:<table>a dataset's source
    column:<table>.<col>a column a field names
    dataset:<name>datasets[]
    field:<dataset>.<name>fields[]
    metric:...dataset or model metrics
    • Node ids carry their kind, so names never collide.
    • Edges point from what is needed to what needs it.
    • A networkx DiGraph, built by build() in lineage.py.
    • Joins are kept in G.graph["joins"], not as edges.
    Every node id starts with its kind, so a table and a metric with the same name do not clash. Edges follow dependency direction. Joins are stored apart because they are not lineage.

    References, never guessed

    • sqlglot reads references, using the spec's scoping rules:
    • a field's SQL names columns of its dataset's source
    • a dataset-scoped metric names that dataset's fields, unqualified
    • a model-scoped metric names dataset.field (or dataset.metric)
    • Unresolved references go into G.graph["problems"]; they are never guessed.
    -- a model-scoped metric over a dataset-scoped one
SUM(store_sales.total_quantity)
    Lineage is only as good as the references behind it. data-graph parses expressions with sqlglot and follows the scoping rules from the spec. Anything it cannot resolve is reported as a problem and not filled in.

    Lineage and impact

    # upstream: what a metric is made of, down to source columns
dgr lineage model.yaml total_sales

# downstream: the metrics a column feeds
dgr impact model.yaml store_sales.ss_ext_sales_price
    • A name can be a metric (total_sales)
    • or a dataset-scoped metric or field (store_sales.total_quantity), or a dataset
    • or a node id (column:tpcds.public.store_sales.ss_quantity)
    Lineage walks up the graph to source columns. Impact walks down to show which metrics a change would affect. Names are resolved flexibly, and you can always fall back to a full node id.

    Checks and exit codes

    • dgr validate: the JSON Schema for the file's Ossie version, then reference, join and gap checks.
    • dgr check: references, joins and gaps only, with no schema.
    • --strict on validate: warnings fail too.
    • Checks find unknown references, joins to undeclared datasets or fields, and metrics over datasets with no join path.
    exitmeaning
    0ok
    1model errors (or an unchecked answer)
    2usage or load error
    validate is the full check and check is the fast one. The exit codes are fixed, so either command can run in CI.

    Draft and profile, read-only

    # a skeleton model from a SQLite catalogue
dgr draft --sqlite shop.db -o shop.semantic_model.yaml

# rows, nulls, distinct, ranges, metric values
dgr profile model.yaml --sqlite shop.db
    • Both go through dd-db with SQLiteDB(path, read_only=True): mode=ro plus PRAGMA query_only.
    • Databases are only ever opened read-only.
    • Only BaseDB methods are used, so other dd-db adapters can follow.
    draft gives you a starting model from an existing database. profile looks at the data behind a model. Neither one can write to the database.

    Export and drawing

    # zinet graph.yaml, or --format json
dgr export model.yaml --format zinet -o lineage.graph.yaml

# or --format mermaid / ascii / svg / png
dgr render model.yaml -o lineage.html
    • In the zinet export, sources and columns are primitives and the model is the one application.
    • Drawing goes through zinet, the graph format the digital-duck family shares.
    The graph can leave data-graph in two ways: as zinet's graph.yaml or as plain JSON. render draws it in several formats through zinet.

    LLM work lives in GraphLang recipes

    • No LLM calls in the library. LLM steps are GraphLang recipes: ask and ossie_draft.
    • The model is chosen with --llm ADAPTER[:MODEL]: default claude_cli, or ollama:llama3.2 to run locally.
    • SOLVE steps run as python3 -I -m datagraf.tool STEP, with JSON on stdin and stdout.
    • A recipe step that writes is risky: true, behind a Cedar GUARD.
    • Tests drive the recipes with a scripted model (an object with generate()), never a real one.
    The library is plain code with tests. Anything that needs a model lives in a recipe, and the program half of each recipe is ordinary Python. That split is why the tests need no network and no LLM.

    The ask recipe

    dgr ask model.yaml "top 5 customers by money spent" --sqlite shop.db
    • Context: only the datasets the question names, plus the join paths between them (--scope all shows everything).
    • The SQL must be one read-only statement over real tables and columns, and it must run.
    • A failure goes back to the model up to --max-repairs times.
    • The report says CHECKED or FAILED, and a program decides which.
    This is the answer to the trust problem. The model sees a narrow context, and its SQL is checked against the model and actually run. The verdict comes from check_sql and report in ask.py, not from the LLM.

    The ossie_draft recipe

    dgr draft --sqlite shop.db --enrich -o shop.semantic_model.yaml
    • Starts from the skeleton, then adds descriptions, synonyms, dimensions and metrics.
    • It may not change what the catalogue says: check() confirms the structure is unchanged.
    • Every metric must run on the data.
    • The write sits behind a Cedar policy: an absolute path under your home or the temporary folder, never over an existing file unless asked.
    The LLM gets to enrich the model, not rewrite it. The program checks the result before it is written, and a policy limits where it can be written.

    Demo: the Chinook model

    examples/chinook.semantic_model.yaml is the Chinook sample database (the one data-copilot used), drafted with dgr draft and then given descriptions, synonyms and metrics by hand.

    dgr show examples/chinook.semantic_model.yaml
dgr lineage examples/chinook.semantic_model.yaml METRIC
dgr ask examples/chinook.semantic_model.yaml "..." \
    --sqlite chinook.sqlite3
    Demo show the model, pick a metric from the output and trace its lineage, then ask a question and read the CHECKED / FAILED report
    Start with show for the datasets, fields, metrics and joins. Pick a metric from that output for lineage. Then ask a question and point out which datasets were sent to the model and how the verdict was reached.

    From Python

    import datagraf as dg

model = dg.load("tpcds_semantic_model.yaml")
G = dg.build(model)   # networkx DiGraph
up = dg.upstream(G, dg.resolve(G, "customer_lifetime_value"))
problems = dg.model_problems(model, G)
    • The graph runs source → column → field → metric.
    • The CLI is a thin click group over the same functions.
    Everything the CLI does is also available as a library, which data-copilot never had. The graph is plain networkx, so any graph algorithm works on it.

    Part of the digital-duck stack

    • zinet graph format and drawing
    • dd-db database access, read-only
    • GraphLang over dd-llm, for the LLM steps
    • Siblings: app-graph, work-graph, concept-book

    Why its own package

    Profiling and running SQL touch the data, which needs credentials and connectors.
    work-graph stays a files-only knowledge layer.
    data-graph reuses the shared stack and does not write its own versions. It is not a work-graph area because it has to reach real databases.

    What is not done yet

    • A prototype at version 0.1.0.dev1, not yet published on PyPI.
    • A model in another dialect is opaque: its lineage cannot be read from SQL.
    • Only SQLite so far; other dd-db adapters can follow, since only BaseDB methods are used.
    • The thin data area in work-graph, which would call data-graph's reader, is planned.
    This was started on 2026-11-22 and is early. Non-SQL dialects and other databases are the obvious gaps. The design and next steps are in docs/DEV/plan.md.
